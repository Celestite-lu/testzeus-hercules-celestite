# 面试问答弹药库 — 「录制即用例」（通俗版）

> 这份文件是什么：40 道面试官最可能问的问题（38 正题 + 2 补充题），每题给出可以直接背的口语化回答。面试前按"最危险题自查清单"（文末）重点过一遍。
> 三类面试官（后文用简称）：**技术官** = AI Agent 方向的技术面试官，考你懂不懂技术；**测开官** = 测试开发方向的面试官，考测试功底；**诚信官** = 专门抠数字真实性的面试官，任何一个数字口径含糊都会被他追杀。
> 每题五要素：问题原话 → **他为什么问**（一句白话）→ **参考回答**（说出来的话，30-60 秒）→ **可能的追问与接法** → **千万别踩的坑** → 出处 / 难度★ / 出现概率%。
> 术语解释见 `resume.md` §0（口径、零样本文本-DOM、单 seed、md 表、无效格、clean 口径等十个词）。

## 开场三件套（任何面试先用三句话把项目钉住）

1. **一句话定位**：开发者点一遍页面 → 确定性规则蒸馏成 Gherkin 用例（骨架零 LLM）→ Hercules 语义化自主执行（UI 改版不挂）→ 失败时规则签名 + LLM 读证据归因定责。击中前端组两个痛点：用例生产成本约等于零、selector 腐烂维护成本约等于零。（PLAN §0）
2. **两个硬数字**：受控变异实验中标识符随机化下生成用例存活 6/6、selector 基线 0/6（主指标 1.00 vs 0.667）；MiniWoB++ 全量 125 任务四轮迭代 43.2%→61.6%，越出公开可比带（47-60%）上沿。（exp §2、r4 §1）
3. **规模信号**：492 条离线测试、四轮全量实验每轮 9-13M token、每轮实验前后双安全审查五类作弊扫描全零。（audit §0/§3）

# 一、项目深挖（12 题）

### Q1 "先讲讲整体架构，为什么这么分层？"
- **他为什么问**：技术官 30 秒内判断你是"调包侠"还是真懂分层取舍；分层的理由必须能落到"出了什么问题所以这么切"。
- **参考回答**：四段链路各管一件事：录制器（注入式 JS，产出 JSON 事件流，密码掩码、hover/scroll 去噪）→ 蒸馏器（规则模板出骨架，LLM 只润色，事实回查兜底）→ 执行内核（复用开源 Hercules：planner→executor→assertion 的 LangGraph 编排，每次现场感知 DOM、按语义属性选元素，不存 selector）→ 归因器（13 条规则签名定类优先，LLM 只做模糊区的证据摘要，引用强制回查）。最外面是子进程编排 CLI 把四命令串起来。分层的原则是一句话："正确性关键路径全部确定性化，LLM 只放在坏了可回退的位置。"（PLAN §3、dspec §2/§4、aspec §3/§4）
- **可能的追问**："为什么执行内核不自研？"→ 见 Q7。"四命令是哪四个？"→ record / generate / run / analyze（--dry-run 可以离线演示）。
- **千万别踩的坑**：不要把 Hercules 的东西说成自己写的；不要说"LLM 生成用例"——骨架是规则出的，LLM 只润色。
- 出处：PLAN §3、audit §5-A1。难度★★ 出现概率 95%

### Q2 "蒸馏为什么骨架层做到零 LLM？这不是不用 AI 吗？"
- **他为什么问**：技术官考你对"哪里该用模型"的判断力；潜台词是"LLM 不可靠，你怎么保证产物可信"。
- **参考回答**：不是不用 AI，是把 AI 挪到坏了也不伤正确性的位置。骨架是确定性规则模板：每种事件类型一张映射表，URL、文本、值全部来自录制事件流的原文——同样输入跑两次，输出逐字节相同。LLM 只做润色（合并连续输入、改措辞），而且润色稿要过四道闸——输出清洗、结构校验、事实回查、断言存活检查——任何一道不过就整体丢弃、回退骨架，不存在"部分采用"。我宁可产出啰嗦但字字真实的用例，不要漂亮但会编的用例。（dspec §2/§4.3/§5.3、dspec 验收 3）
- **可能的追问**："那 LLM 润色引入过问题吗？"→ 有预案：审查发现兜底词本身可能造成没有出处的字面值，解法是把 element/field/dropdown/form 这些写死常量列入回查豁免。（distiller/review.md P0）
- **千万别踩的坑**：别说"LLM 不重要"；变异实验里生成侧就是纯模板跑的，别说成 LLM 生成。（exp §1）
- 出处：dspec §2/§4/§5、audit §5-C9。难度★★ 出现概率 90%

### Q3 "事实回查具体怎么做的？怎么防 LLM 幻觉？"
- **他为什么问**：技术官验证你说的"防幻觉"是真机制还是话术，要能讲到算法级。
- **参考回答**：三层。第一，事实集在模板生成之前就从事件流构建好：每个 URL、每个输入值、每个元素的 name/label、每条断言文本，都是 ground truth（可信原稿）。第二，回查算法：提取产物里所有引号内的字面值，规范化后要求每条要么精确等于某条事实、要么是某条事实的子串（允许子串是为了容忍润色截取长句）；占位符、空串、模板兜底常量豁免。第三，润色稿不过回查就整体回退骨架，回退原因里列出具体哪个字面值没过。骨架本身由事实集生成、按构造必然通过——骨架自检失败说明校验器有 bug，直接抛错而不是静默兜底。（dspec §5.1-5.3、§2.5）
- **可能的追问**："匹配是模糊匹配吧？会不会放过幻觉？"→ 是规范化后的空白折叠+大小写敏感子串匹配，方向固定是"产物 ⊆ 事实"，宽严有明确定义；测试里有注入 `http://evil.example` 被拦住的用例。（dspec 用例 20/25）
- **千万别踩的坑**：不要说"用另一个 LLM 检查"——回查是纯程序、零模型，这是卖点。
- 出处：dspec §5、§7 验收 5。难度★★★ 出现概率 80%

### Q4 "断言是 LLM 编出来的吧？可靠性怎么保证？"
- **他为什么问**：技术官/测开官考 grounding（每个字有出处）的概念；测开官会接着问"文案改了断言红了算谁的"。
- **参考回答**：断言不来自模型想象，来自录制时的真实 DOM 快照——每个事件发生后 300 毫秒抓一次页面可见文本做差集，存进事件流的 assert_texts，蒸馏时一一变成 `Then I should see`。所以断言的可靠性等于录制的可靠性。有个必讲的边界：文案改写变异下 5/6，唯一失败的格子是断言绑定了录制时的原文案"去下单"、页面改成"马上下单"后断言红——这是**测试的正确行为**，不是缺陷；那一格的操作步骤全部语义映射成功，而且归因器规则层直接定位到 `Missing: '去下单' (found '马上下单')`。（PLAN §3.1、exp §3-2、rtrep §178）
- **可能的追问**："300 毫秒快照会不会归错事件？"→ 会，这正是我修过的 bug，见 Q8 的快照归因缺陷故事，答出来反而加分。
- **千万别踩的坑**：不要吹"断言永远准"；文案改写的边界要主动并列讲，这是量化过的边界不是藏着的问题。
- 出处：PLAN §3.1、exp §3、audit §5-C10。难度★★ 出现概率 85%

### Q5 "归因器怎么保证不瞎编？LLM 归因不就是在猜吗？"
- **他为什么问**：技术官/诚信官的核心考点：agent 输出不可信时怎么工程化兜底；诚信官在看你会不会让 LLM 编故事。
- **参考回答**：三层防线。一，规则签名优先：13 条签名对引擎的固定错误串做匹配，命中即定类，LLM 完全不参与——比如 planner 轮次耗尽判"agent 能力上限"、元素找不到判"用例过时"（低置信还强制附替代假设）。二，只有"产品 bug 还是用例过时"这类模糊区才交给 LLM，输入是编号好的证据包（日志轮次/截图文件名/JUnit 原文），输出 JSON 里的每条引用由程序回查：引用号不存在、轮次越界、摘录不是原文子串，一律丢弃。三，回查后没有存活的文本证据就强制降级"无法定位"，置信度压到 0.30，原始证据保留可查——prompt 里明写"宁可疑而不定，不许猜"，"无法定位"是合法且被鼓励的输出。五个档位：产品 bug / 用例过时 / 环境 / agent 能力上限 / 无法定位。（aspec §3.2/§4.4/§4.5）
- **可能的追问**："规则能覆盖多少？"→ 13 条签名 + 兜底路由；真实失败样本上规则层直接定过类（文案改写那格是 S10 签名、无 LLM 降级产出正确报告）；签名召回率的系统统计列为后续项，不吹全覆盖。（aspec §9/§10、exp §3-3）
- **千万别踩的坑**：别说"LLM 负责归因"——LLM 只负责模糊区摘要；规则层/证据层/报告层是零模型 import 的（grep 可验）。
- 出处：aspec §3/§4、exp §3-3、audit §5-C11。难度★★★ 出现概率 90%

### Q6 "为什么用子进程编排，不直接进程内跑？"
- **他为什么问**：技术官考工程判断有没有实证依据，还是拍脑袋。
- **参考回答**：第一天就定死子进程，因为进程内有四个实证的坑：第一，上游的 StaticLTM 是单例，第二个 feature 会拿到第一个的测试数据——串场；第二，config 单例重置会丢内存态；第三，输出目录用 import 时的时间戳，证据会混叠；第四，PlaywrightManager 的关闭是发后不管，和下一个场景的启动有竞态。而且上游自己的 MCP server 都回避进程内执行、用的就是子进程模式，我照抄了这个成熟先例。子进程还白送三样东西：超时可杀、崩溃不传染、天然可并行。（PLAN §3.3）
- **可能的追问**："代价呢？"→ 每个场景多一次浏览器/引擎冷启动，单场景约 60 秒起、简单流程 7.3 万 token，成本账见 Q34。
- **千万别踩的坑**：单例串场要讲成"我审查源码查出来的坑"，不是背书——这是二开前源码审查的实证结论。（PLAN §3.3）
- 出处：PLAN §3.3、audit §5-D13 旁证。难度★★ 出现概率 75%

### Q7 "为什么基于 Hercules 二开，不自己写执行内核？"
- **他为什么问**：技术官考技术选型与贡献边界意识，也为 Q27 铺垫。
- **参考回答**：两周约束内自研 agent 内核不可能达到可评测的质量，与其造烂轮子，不如站在一个能讲清楚的开源内核上做增量。选它有三个标准：一，LangGraph 编排清晰可讲（planner→executor→assertion）；二，它的语义选择机制和我的录制器取属性同源对齐（aria-label/label/placeholder/innerText 同一取值顺序），蒸馏产物天然是引擎能定位的措辞；三，AGPL 许可对秋招展示无碍。二开纪律：不改上游主包，benchmark 需要的引擎改动全部做成开关且默认关闭，关闭状态用 golden 文件逐字节锁定——"上游行为零漂移"是可验证的。（PLAN §2/§6、r4 §5、audit §5-C12）
- **可能的追问**："你改过引擎吗？"→ 第二轮起有引擎开关化补丁（终局信号、单次开局等），但全部默认关 + 回放锁定，且是申报过的接线点，不是偷偷改。（STATUS 7.6、r4 §5）
- **千万别踩的坑**：不要把 Hercules 的 DOM 蒸馏说成自己设计；但第四轮的元素表扩展是我的改进，可以讲"覆盖超过了 Agent-E 的 all_fields"。（anatomy §2 表 #3）
- 出处：PLAN §2、audit §5-C12、anatomy §5。难度★★ 出现概率 80%

### Q8 "录制器到执行引擎，怎么保证蒸馏出来的用例真的能被执行？"
- **他为什么问**：技术官考端到端思维：两个独立模块的契约怎么对齐、坏了怎么发现。
- **参考回答**：两个机制。一，设计期对齐：录制器取元素名的顺序和引擎感知时的语义属性同源（aria-label→label→placeholder→innerText→title），蒸馏产物的措辞天然落在引擎的定位依据上。二，验证期兜底：录制→蒸馏→执行的迭代线，变异实验首轮通过率 6/6，超过 70% 的目标。另外有个我真踩过的坑：集成冒烟发现 input 事件的 300 毫秒延迟快照会把后续点击才出现的文案归给先入队的 input，蒸出"Then 出现在状态变化之前"的用例，重放必然假失败——20 条单测全绿都没拦住，因为只测了"点击后包含"、没测"点击前排除"。修复是快照归属改成"触发时刻最新事件"，并补了排除性断言。教训：单测覆盖语义等价类之外，集成冒烟必须保留。（PLAN §3.1、rtrep 补记、STATUS D1）
- **可能的追问**："还有别的契约坑吗？"→ submit 双事件契约，见 Q9；录制节奏慢于 450 毫秒会把多动作压进最后一个事件，真人手速天然满足。（etrep 已知#6）
- **千万别踩的坑**：这个故事的好结尾是"单测为什么没拦住"——答不出这点，故事就白讲了。
- 出处：PLAN §3.1、rtrep 补记、STATUS D1、audit §1。难度★★★ 出现概率 70%

### Q9 "submit 双事件契约是怎么回事？"（或"录制和蒸馏的契约怎么定的？"）
- **他为什么问**：技术官考 schema 契约设计与边界所有权的清晰度。
- **参考回答**：录制器对一次提交按钮的点击恒产出两条事件：click（第 N 条）+ submit（第 N+1 条），这是录制的既定契约。但 submit 事件落在跳转后的页面上，元素通常取不到名字，直接蒸会产出冗余步骤。解法放在蒸馏器规则层：确定性去重——"紧邻前驱是 click"的 submit 丢弃自身步骤、保留 click 步骤（它带按钮名字，定位更有价值），但 submit 的断言照常生成。为什么放规则层不放 LLM 润色层？因为它是确定性规则、零模型依赖，属于骨架层职责。submit 的回车键形态（前驱是 input）不适用去重，照常生成。（dspec §2.2 P0-1、distiller/review.md）
- **可能的追问**："这是计划里没有的？"→ 对，总计划的映射表没覆盖 submit，设计文档里标为补充定义、评审时和录制器契约逐条对齐过——没有静默漂移。（distiller/review.md §表）
- **千万别踩的坑**：别说"LLM 自动合并掉了"——去重是规则层干的，这是设计品味的考点。
- 出处：dspec §2.2、distiller/review.md。难度★★★ 出现概率 55%

### Q10 "benchmark 的测试工具是怎么搭的？怎么保证 125 格成绩可比可复现？"
- **他为什么问**：技术官/测开官考评测基建素养：seed 管理、口径、断点续跑。
- **参考回答**：核心是确定性。每格的随机种子由 `sha1(实验ID:miniwob:任务ID)` 派生，同一实验 ID 重跑同种子；任务集取 browsergym registry 全量 125 个任务类，不做挑选。判分权威是页面原生 `WOB_RAW_REWARD_GLOBAL > 0`，无 LLM 裁判；own-seed 过滤保证 planner 写错种子的页面做到了也不计分；off-seed 信标检测种子透传失败。每格结果行带导航计数、file:// 记录、沙箱扫描标记，断点续跑同命令。结果同时出三个口径：官方（最后一次生效）、首实例（防重试灌水）、零重导航子集（诚实性指标）。全流程产出 manifest + results.jsonl + rewards.jsonl，终审可以逐行复算——事实上终审真的把变异实验的 60 格逐行复算过，分毫不差。（r1 §1/§6、sec1p V9、r2a §5、final §0）
- **可能的追问**："三口径为什么不一致？"→ 第二轮起两口径相等（零洗白），第四轮官方=干净首次统一；历史上第一轮差 5 格是引擎超时覆盖了页面已通过的判分瑕疵，第二轮修复后为 0。（r2a §5/§6）
- **千万别踩的坑**：别把 125 说成"125 个实例"——是 125 个任务类各跑 1 个实例；HxAgent 才是 5 个任务族×25 实例。（anatomy §1.2）
- 出处：r1 §1、R2F §1、sec1p、audit §6。难度★★★ 出现概率 70%

### Q11 "61 格超时这种性能问题，你是怎么定位到根因的？"
- **他为什么问**：技术官考 profiling 方法论：是猜的还是测的。

- **可能的追问**："我们页面很复杂（iframe/微前端）？"→ 如实给边界：跨域 iframe/closed shadow DOM 是录制层硬盲区，先盘页面形态再谈接入；这恰好是试点选型要做的第一件事。（PLAN §3.1/§4）
- **千万别踩的坑**：不要承诺替代人工测试；定位是"用例生产+维护+定责"三个环节的成本压缩。

### Q34 "算过成本账吗？这套东西跑一次多少钱？"

### Q35 "如果要支持多团队并行跑，架构要怎么改？"
- **他为什么问**：技术官/测开官考平台化想象力的落地性。
- **参考回答**：地基已经有了：子进程隔离让每个 feature 天然独立进程，崩溃不传染、超时可杀，并行化主要是编排层扩容——worker 池 + 每任务独立项目根（EXECUTE_BULK 模式已把每个子目录当独立项目基座）。三个要补的点都有实证依据：一，共享单例全部消除了（StaticLTM/config/时间戳目录就是当初选子进程的原因），但浏览器实例池要自己管；二，配速与熔断——第二轮实战过 429 熔断 + --max-cells 配速，多租户下升级为每租户配额；三，沙箱租户隔离——引擎有租户 ID 机制，但我实测过 restricted 档不是安全边界，多租户必须先堵这个（环境开关或容器级隔离）。结果回收靠 JUnit+证据目录，天然可对接对象存储。（PLAN §3.3、r2 §1、sec1p V6、AGENTS.md 沙箱节）
- **可能的追问**："LLM 端点限流怎么办？"→ 第二轮的分段执行 + 429 熔断 + 逐尝试日志就是单租户版答案，多租户按租户加权即可。（r2 §1、r1 §4）
- **千万别踩的坑**：不要把"多租户"答成纯架构八股——引用自己实测过的沙箱逃逸发现才有说服力。
- 出处：PLAN §3.3、sec1p V6、r2 §1。难度★★★ 出现概率 60%

### Q36 "和 Playwright codegen / Selenium 录制的本质区别到底是什么？"
- **他为什么问**：测开官第一对比题。要一句话打出本质，再用数据支撑。
- **参考回答**：一句话：codegen 录的是"怎么点"（selector，一次成型、页面一改就失效），我录的是"点什么"（自然语言意图+语义断言，每次执行现场理解 DOM）。后果三条：改版存活率——标识符随机化下 6/6 vs 0/6（实验实证，不是空谈）；可读性——Gherkin 用例人和 agent 都能读，能进 PR 评审；失败语义——codegen 挂了只有红色报错，我有归因定类（产品 bug/用例过时/环境/agent 能力上限）。代价也如实：执行慢且贵（60 秒起/数万 token，对比毫秒级回放），所以定位是回归层的价值验证，不是替代秒级冒烟回放。（audit §5-A1、exp §3、PLAN §6）
- **可能的追问**："那为什么不录两份，codegen 跑快路径、挂了再语义重跑？"→ 这是个好方向，相当于把语义执行当自愈兜底；我的归因器恰好能当这个调度器的判据（先判用例过时再触发重录/重跑）。承认没做，归入后续。（aspec §3.3）
- **千万别踩的坑**：别把区别说成"我们用了 AI 所以更好"——本质是"意图层 vs 定位层"的表示差异，AI 是实现手段。
- 出处：audit §5-A1、exp §3、PLAN §6。难度★★ 出现概率 90%
