# 一、项目深挖（12 题）

### Q1 "先讲讲整体架构，为什么这么分层？"
- **意图**：T官。30 秒内判断你是"调包侠"还是真懂分层取舍；分层理由必须能落到"出了什么问题所以这么切"。
- **答案要点**：四段链路各管一件事：录制器（注入式 JS 出 JSON 事件流，密码掩码、hover/scroll 去噪）→ 蒸馏器（规则模板出骨架，LLM 只润色，事实回查兜底）→ 执行内核（复用开源 Hercules：planner→executor→assertion 的 LangGraph，每次现场感知 DOM 按 md 语义属性选元素，不存 selector）→ 归因器（13 条规则签名定类优先，LLM 只做模糊区的证据摘要，引用强制回查）。外层子进程编排 CLI 串四命令。分层原则是"正确性关键路径全部确定性化，LLM 只放在坏了可回退的位置"。（PLAN §3、dspec §2/§4、aspec §3/§4）
- **追问与二线防线**："为什么执行内核不自研？"→ 见 Q7。"四命令是哪四个？"→ record / generate / run / analyze（--dry-run 可离线演示）。（final §2）
- **翻车点**：不要把 Hercules 的东西说成自己写的；不要说"LLM 生成用例"——骨架是规则出的，LLM 只润色。
- 出处：PLAN §3、audit §5-A1。难度★★ 出现概率 95%

### Q2 "蒸馏为什么骨架层做到零 LLM？这不是不用 AI 吗？"
- **意图**：T官。考你对"哪里该用模型"的判断力；潜台词是"LLM 不可靠，你怎么保证产物可信"。
- **答案要点**：不是不用 AI，是把 AI 挪到坏了不伤正确性的位置。骨架是确定性规则模板：每种事件类型一张映射表，URL/文本/值全部来自录制事件流原文，同输入两次运行逐字节相同；LLM 只做润色（合并连续 input、改措辞），且润色稿要过四道闸——输出清洗、结构校验、事实回查、断言存活检查，任一失败整体丢弃回退骨架，不存在"部分采用"。我宁可产出啰嗦但字字真实的用例，不要漂亮但会编的用例。（dspec §2/§4.3/§5.3、dspec 验收 3）
- **追问与二线防线**："那 LLM 润色引入过问题吗？"→ 有预案：审查发现兜底词本身可能造成未 grounding 字面值，解法是把 element/field/dropdown/form 写死常量列入回查豁免。（distiller/review.md P0）
- **翻车点**：别说"LLM 不重要"；exp001 里 generated 侧就是纯模板跑的，别说成 LLM 生成。（exp §1）
- 出处：dspec §2/§4/§5、audit §5-C9。难度★★ 出现概率 90%

### Q3 "事实回查具体怎么做的？怎么防 LLM 幻觉？"
- **意图**：T官。验证你说的"防幻觉"是真机制还是话术；要能讲到算法级。
- **答案要点**：三层。第一，事实集在模板生成前从事件流构建：每个 URL、每个输入值、每个元素 name/label、每条断言文本都是 ground truth。第二，回查算法：提取产物里所有引号内字面值，规范化后要求每条精确等于或属于某条事实的子串（子串方向是为容忍润色截取长句）；占位符、空串、模板兜底常量豁免。第三，润色稿不过回查就整体回退骨架，fallback_reason 里列出具体哪个字面值没过。骨架由事实集生成、按构造恒过——骨架自检失败说明校验器有 bug，直接抛错而不是静默兜底。（dspec §5.1-5.3、§2.5）
- **追问与二线防线**："匹配是模糊匹配吧？会不会放过幻觉？"→ 是规范化后的空白折叠+大小写敏感子串，方向固定 L⊆F，宽严有明确定义；测试里有注入 `http://evil.example` 被拦的用例。（dspec 用例 20/25）
- **翻车点**：不要说"用另一个 LLM 检查"——回查是纯程序、零模型，这是卖点。
- 出处：dspec §5、§7 验收 5。难度★★★ 出现概率 80%

### Q4 "断言是 LLM 编出来的吧？可靠性怎么保证？"
- **意图**：T官/测官。考 grounding 概念；测官会接着问"文案改了断言红算谁的"。
- **答案要点**：断言不来自模型想象，来自录制时真实 DOM 快照——每个事件入队后 300ms 抓取页面可见文本做差集，存进事件流的 assert_texts，蒸馏时一一变成 `Then I should see`。所以断言的可靠性等于录制的可靠性。有个必讲的边界：M4 文案改写变异下 5/6，唯一失败格是断言绑定了录制时原文案"去下单"、页面改成"马上下单"后断言红——这是**测试的正确行为**，不是缺陷；该格操作步骤全部语义映射成功，且归因器规则层直接定位到 `Missing: '去下单' (found '马上下单')`。（PLAN §3.1、exp §3-2、rtrep §178）
- **追问与二线防线**："300ms 快照会不会归错事件？"→ 会，这正是我修过的 bug，见 Q10/Q8 的快照归因缺陷故事，答出来反而加分。（rtrep 补记）
- **翻车点**：不要吹"断言永远准"；M4 边界要主动并列讲，这是量化过边界而非藏雷。（final §3-1）
- 出处：PLAN §3.1、exp §3、audit §5-C10。难度★★ 出现概率 85%

### Q5 "归因器怎么保证不瞎编？LLM 归因不就是在猜吗？"
- **意图**：T官/诚官。核心考点：agent 输出不可信时怎么工程化兜底；诚官在看你会不会让 LLM 编故事。
- **答案要点**：三层防线。一，规则签名优先：13 条签名对引擎固定错误串做匹配，命中即定类，LLM 完全不参与——比如 planner 轮次耗尽判 agent_limit、元素 not found 判用例过时（低置信还强制附替代假设）。二，只有"产品 bug vs 用例过时"这类模糊区才交 LLM，输入是编号好的证据包（日志轮次/截图文件名/JUnit 原文），输出 JSON 里的每条引用程序回查：引用号查无、轮次越界、摘录不是原文子串，一律 drop。三，回查后没有存活文本证据就强制降级"无法定位"，置信度压到 0.30，种子证据保留可查——prompt 明写"宁可疑而不定，不许猜"，无法定位是合法且被鼓励的输出。五类：产品 bug / 用例过时 / 环境 / agent 能力上限 / 无法定位。（aspec §3.2/§4.4/§4.5）
- **追问与二线防线**："规则能覆盖多少？"→ 13 签名 + fallback 路由，真实失败 F5/M4 上规则层 S10 直接定类、无 LLM 降级产出正确报告；签名召回率的系统统计列为后续项，不吹全覆盖。（aspec §9/§10、exp §3-3）
- **翻车点**：别说"LLM 负责归因"——LLM 只负责模糊区摘要；规则层/证据层/报告层是零模型 import 的（grep 可验）。
- 出处：aspec §3/§4、exp §3-3、audit §5-C11。难度★★★ 出现概率 90%

### Q6 "为什么用子进程编排，不直接进程内跑？"
- **意图**：T官。考工程判断有没有实证依据还是拍脑袋。
- **答案要点**：第一天就定死子进程，因为进程内有四个实证的坑：StaticLTM 是单例，第二个 feature 会拿到第一个的测试数据——串场；config 单例 reset 丢内存态；输出目录用 import 时时间戳，证据会混叠；PlaywrightManager 关闭是 fire-and-forget，和下一个场景启动有竞态。而且上游自己的 MCP server 都回避进程内执行、用的就是子进程模式，我照抄了这个成熟先例。子进程还白送三样东西：超时可杀、崩溃不传染、天然可并行。（PLAN §3.3）
- **追问与二线防线**："代价呢？"→ 每个场景多一次浏览器/引擎冷启动，单场景约 60s+、简单流程 7.3 万 token，成本账见 Q34。（STATUS 阶段 6、exp §2）
- **翻车点**：static_ltm 串场要讲成"我审查出来的坑"而不是背书——这是 r2 之前源码审查的实证结论。（PLAN §3.3）
- 出处：PLAN §3.3、audit §5-D13 旁证。难度★★ 出现概率 75%

### Q7 "为什么基于 Hercules 二开，不自己写执行内核？"
- **意图**：T官。考技术选型与贡献边界意识；也为 Q27 铺垫。
- **答案要点**：两周约束内自研 agent 内核不可能达到可评测质量，与其造烂轮子不如站在能讲清楚的开源内核上做增量。选它的三个标准：LangGraph 编排清晰可讲（planner→executor→assertion）；它的 md 语义选择机制和我的录制器取属性同源对齐（aria-label/label/placeholder/innerText 同一取值顺序），蒸馏产物天然是引擎能定位的措辞；AGPL 对秋招展示无碍。二开纪律：不改 testzeus_hercules/ 主包，benchmark 需要的引擎改动全部做成 flag 且默认 off，off 状态用 golden 文件逐字节锁定——保证"上游行为零漂移"可验证。（PLAN §2/§6、r4 §5、audit §5-C12）
- **追问与二线防线**："你改过引擎吗？"→ r2 起有引擎 flag 化补丁（终局信号、单次开局等），但全部默认 off + 回放锁定，且这是申报过的接线点，不是偷偷改。（STATUS 7.6、r4 §5）
- **翻车点**：不要把 Hercules 的 DOM 蒸馏说成自己设计；但 r4 的 --md-extended（终表扩展）是我的改进，可以讲"超出 Agent-E all_fields 覆盖"。（anatomy §2 表 #3）
- 出处：PLAN §2、audit §5-C12、anatomy §5。难度★★ 出现概率 80%

### Q8 "录制器到执行引擎，怎么保证蒸馏出来的用例真的能被执行？"
- **意图**：T官。考端到端思维：两个独立模块的契约怎么对齐、坏了怎么发现。
- **答案要点**：两个机制。一，设计期对齐：录制器 target.name 的取值顺序和引擎感知时的语义属性同源（aria-label→label→placeholder→innerText→title），蒸馏产物的措辞天然落在引擎的定位依据上。二，验证期兜底：蒸→跑→改的迭代线，exp001 首轮通过率 6/6 超过 70% 目标。另外有个我真踩过的坑：集成冒烟发现 input 事件的 300ms 延迟快照会把后续点击才出现的文案归给先入队的 input，蒸出"Then 出现在状态变化之前"的用例，重放必假失败——20 条单测全绿都没拦住，因为只测了"点击后包含"没测"点击前排除"。修复是快照归属改成"触发时刻最新事件"，并补了排除性断言。教训：单测覆盖语义等价类之外，集成冒烟必须保留。（PLAN §3.1、rtrep 补记、STATUS D1）
- **追问与二线防线**："还有别的契约坑吗？"→ submit 双事件契约，见 Q10；录制节奏 <450ms 会把多动作压缩进最后一个事件，真人手速天然满足。（etrep 已知#6）
- **翻车点**：这个故事的好结尾是"单测为什么没拦住"——答不出这点故事就白讲了。
- 出处：PLAN §3.1、rtrep 补记、STATUS D1、audit §1。难度★★★ 出现概率 70%

### Q9 "submit 双事件契约悬空是怎么回事？"（或"录制和蒸馏的契约怎么定的？"）
- **意图**：T官。考 schema 契约设计与边界所有权的清晰度。
- **答案要点**：录制器对一次提交按钮点击恒产出 click(seq N) + submit(seq N+1) 两条事件，这是录制的既定契约；但 submit 事件落在跳转后的页面上，target 通常取不到 name，直接蒸会产出冗余步骤。解法放在蒸馏器规则层：确定性去重——"紧邻前驱是 click"的 submit 丢弃自身步骤、保留 click 步骤（它带按钮 name，定位更有价值），但 submit 的断言照常生成。为什么放规则层不放 LLM 润色层？因为它是确定性规则，零模型依赖，属于骨架层职责；白名单动作和它不能混。submit 的 Enter 键形态（前驱是 input）不适用去重，照常生成。（dspec §2.2 P0-1、distiller/review.md）
- **追问与二线防线**："这是 PLAN 里没有的？"→ 是，PLAN §3.2 映射表没覆盖 submit，spec 里标为补充定义、review 里和录制器契约逐条对齐过——无静默漂移。（distiller/review.md §表）
- **翻车点**：别说"LLM 自动合并掉了"——去重是规则层干的，这是设计品味的考点。
- 出处：dspec §2.2、distiller/review.md。难度★★★ 出现概率 55%

### Q10 "benchmark 的 harness 是怎么搭的？怎么保证 125 格成绩可比可复现？"
- **意图**：T官/测官。考评测基建素养：seed 管理、口径、断点续跑。
- **答案要点**：核心是确定性：每格 seed 由 `sha1(exp_id:miniwob:task_id)` 派生，同实验 ID 重跑同 seed；任务集取 browsergym registry 全量 125 任务类，不做挑选。判分权威是页面原生 `WOB_RAW_REWARD_GLOBAL > 0`，无 LLM 裁判；own-seed 过滤保证 planner 写错 seed 的页面做到也不计分；off-seed 信标检测种子透传失败。每格结果行带导航计数/file://、沙箱扫描标记，断点续跑同命令续跑。结果三口径同出：官方 last-wins、首实例（防重试灌水）、零重导航子集（诚实性指标）。全流程产出 manifest + results.jsonl + rewards.jsonl，终审可以逐行复算——事实上终审真的复算过 exp001 的 60 格，分毫不差。（r1 §1/§6、sec1p V9、r2a §5、final §0）
- **追问与二线防线**："三口径为什么不一致？"→ r2 起两口径相等（零洗白），r4 官方=clean 首次统一；历史上 r1 差 5 格是引擎超时覆盖页面通过的判分瑕疵，r2 修复后为 0。（r2a §5/§6）
- **翻车点**：别把 125 说成"125 个实例"——是 125 个任务类各 1 实例；HxAgent 才是 5 任务×25 实例。（anatomy §1.2）
- 出处：r1 §1、R2F §1、sec1p、audit §6。难度★★★ 出现概率 70%

### Q11 "61 格超时这种性能问题，你是怎么定位到根因的？"
- **意图**：T官。考 profiling 方法论：是猜的还是测的。
- **答案要点**：逐格时间戳配对做计时分解，不猜。r1 的结论反直觉：planner LLM 只占 4%、实测工具执行约 3%，其余约 93% 是 executor 逐轮微决策延迟——被杀格平均 35-60+ 轮 vs 通过格 18 轮，差距在轮数不在单轮。轮数膨胀一半是任务真需要、一半是失败重试；还有三个放大器：页面终局后引擎不停车平均空转 273 秒、重导航会复位 240 秒页钟（email 系列把页钟续到 584 秒）、helper 60 秒双超时引发 planner 改写步骤级联。r2 换 GLM 后形态又变：中位延迟不高但肥尾，10.3% 的长补全 turn 吃掉 38% 墙钟。这直接指导了 r3 的改进排序：先拆 planner 90 秒超时链（超时 41→21），而不是盲目压单轮延迟。（R1F §2、R2F §2、r3 §2）
- **追问与二线防线**："executor 为什么轮数这么多？"→ 每轮是 hover/click/取 DOM 级微决策；r1 分析还发现引擎强制重感知让轮次双倍（超时格 51.3 轮 vs 通过格 19.9）。（STATUS 2026-09-22 决策）
- **翻车点**：别说"就是 LLM 慢"——r2 数据证明主因是肥尾和级联不是均值延迟，说反了显得没读过自己的数据。
- 出处：R1F §2、R2F §2、r3 §2、STATUS 决策日志。难度★★★ 出现概率 65%

### Q12 "四轮迭代每轮改了什么？凭什么说涨分是你的改进带来的？"
- **意图**：T官/诚官。考归因纪律：改进和成绩之间有没有实证链条。

### Q35 "如果要支持多团队并行跑，架构要怎么改？"

### Q36 "和 Playwright codegen / Selenium 录制的本质区别到底是什么？"
- **意图**：测官第一对比题。要一句话打出本质，再用数据支撑。

- **翻车点**：别把区别说成"我们用了 AI 所以更好"——本质是"意图层 vs 定位层"的表示差异，AI 是实现手段。
