## 2. 归因修正（实验后复审实证）

| 改进 | 实效 | 归因结论 |
|---|---|---|
| R3-1 nav 补全上限 768 | **no-op** | 引擎注入链正常（768 在位），但 **GLM 端点不把 max_tokens 当内容硬上限**（实测 768 下产出 19,349 completion token；215 轮 >768 与 r2 分布同质）。超时减半**不能**归因于它 |
| R3-2 planner 双层 150s | **生效** | 超时 41→21 的主要来源（r2 的 25/41 超时格中招 planner 90s 链） |
| R3-3 drag 透传修复 | **生效** | 拖拽家族 0/9 → 3/9；9/9 选择器解析成功（kill-switch 判据达成） |
| R3-5 安全包 | **全生效** | 零无效格（r2 是 10+1）；persist/recall 全日志零出现；scheme 白名单实拦 4 次（2× javascript:、2× view-source:，涉事格均未通过） |
| R3-6 断言纪律 | 未单独归因 | 与整体合并 |
| R3-4 480s 臂 | **未跑**（另批） | 预估 +6~16 格待验证 |

**持平之谜的解释**：r3 的实际增益（R3-2 救回的超时格 + drag 3 格）被以下抵消：R3-1 无贡献、visual-addition 等边缘格的随机回归（单 seed 单次的固有方差）、以及 r2→r3 同为 GLM 模型无模型侧变化。

## 3. 完整性披露（YELLOW 项）

1. **R3-1 声明失真**：flag 在位但被端点忽略——报告与 manifest 修正为 no-op；r4 若要真上限需换实现（如客户端流式截断）
2. **use-slider-2 off-seed 运行**：planner 剥掉了 URL 的 r2g_seed 参数（timeout 判负，零分值影响）；r4 修补丁层校验
3. 官方与首实例差的唯一 1 格为合法 infra 重试（click-menu-2）

## 4. r4 方向（数据指向）
